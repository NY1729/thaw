## Diagnostics

The runner performs the QuickJS and std preflights, then runs the existing nine wire groups. It next performs the runtime no-run preflight once and runs the ten dependency groups plus the HTTP test `http::tests::peer_send_eof_preserves_pending_streamed_response` as group 50, using the existing std no-run gate. The eleventh stage appends six full-name singleton controls as groups 51–56: four runtime controls gated by the runtime preflight, followed by two WebAssembly controls gated by the QuickJS preflight. The twelfth stage appends two QuickJS singleton controls as groups 57–58, also gated by the QuickJS preflight: `tests::terminal_pending_work_is_separate_from_failure_and_exit_code` and `tests::private_graph_arguments_do_not_revive_user_marker_shapes`. The first 56 filter objects and name gates remain unchanged. These 28 independent groups run before both LLVM checks and the original 30 guarded groups. Each package preflight gates only its own groups; a runtime no-run failure blocks runtime groups, while a QuickJS or std preflight failure does not block unrelated groups. The std preflight result is reused. The original 30 groups, including their historical std control, keep their order and existing predecessor gates. Exact fully qualified names are pinned for all 35 configured independent tests. When a group runs, the runner records its selected and executed names; exact-name checks fail closed on empty, substituted, duplicate, ignored, malformed-summary, partial, or wrong-count results. The runner validates singleton full-name identity; it does not pass a literal `--exact` flag.

The workflow uses one job, build parallelism 2, a 90-minute job cap, and a 70-minute runner cap. Its pinned LLVM setup remains a prerequisite before the runner starts. The inherited 24-owner native draft and product integration remain unreviewed and on HOLD. A passing verifier confirms pinned reconstruction; control results record the selected tests’ observed outcomes. These results do not establish broader integration behavior or close separate runtime and semantic gates.

## Local harness tests

Run the standard-library-only harness tests with:

```sh
python3 -m unittest discover -s .ci/native-return-v1/tests -v
```

These tests use synthetic Git fixtures and do not run Rust/Cargo, install dependencies, download LLVM, or contact a network service. The GitHub workflow installs the pinned LLVM asset only on its runner. A green harness test result confirms harness behavior, not product compilation or runtime behavior.
